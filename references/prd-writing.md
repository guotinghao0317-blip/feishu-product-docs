# PRD 写作标准

新写或修订飞书 PRD 时，直接按本标准写作。根据任务和可核实的业务事实开始，无需等待参考 PRD。假定读者是一位熟悉行业、第一次接触这项业务的从业者。读者没有内部背景，也没参与此前讨论。写完后，用这个视角读一遍。

开头先交代业务对象、用户在哪个场景遇到问题、本次为什么改。内部术语、缩写和版本简称首次出现时，顺手解释它和当前需求的关系。关键背景直接写在正文中，读者仅阅读这份 PRD 就能跟上。

## 一、每份 PRD 要写什么

标题下用 2–4 条高亮要点交代本次改动和关键范围。正文至少覆盖背景与目标、范围、关键策略、验收。数据和待确认项按实际需要补充。章节可以合并，下面的问题仍需在适用处回答。一级标题用中文序号加顿号，例如「五、验收与待确认」。二级标题沿用父章节号，从「5.1 验收标准」到「5.2 待确认事项」依次编号。

| 章节 | 应回答的问题 | 写到什么程度 |
| --- | --- | --- |
| 一、背景与目标 | 为什么要改？改动落在哪个版本？ | 写清现有问题、影响或量级、团队做出的决定和目标版本。保留真正影响决策的例子、前置条件和历史节点。 |
| 二、数据与影响 | 这个判断有多大把握？ | 有数据时写日期、对象、统计的事件、分母或去重方式，再说它支持哪项决定、还缺哪项数据。无需跑数的简单需求可合并到背景。 |
| 三、范围与能力变化 | 哪些保留、调整、下线？ | 先用清单或表格定范围，必要时标出适用版本、车型、入口或用户。容易混淆的指令或入口单独区分。 |
| 四、详细策略 | 用户做了什么，系统具体怎么响应？ | 按功能写，遇到状态或目标不同且结果不同的场景就拆分支。用下节的写法。 |
| 五、验收与待确认 | 测试怎么判断通过？哪些规则还没定？ | 覆盖主流程、关键边界和历史缺陷。每项待确认写明它影响哪个场景或验收。 |

## 二、每条关键策略的六个必备项

以下场景使用虚构的视频应用。

| 必备项 | 写清什么 | 一句示例 |
| --- | --- | --- |
| 触发 | 用户说了什么、做了什么，或系统什么时候自动触发 | 用户说「下一集」。 |
| 前置条件 | 动作在什么状态或限制下成立 | 当前有可控制的示例视频应用会话，且存在下一集。 |
| 执行对象 | 系统要操作哪个应用、内容、会话或设备 | 操作当前的示例视频应用播放器。 |
| 系统动作 | 系统具体做什么，操作前后状态如何变化 | 切到相邻的下一集并开始播放。 |
| 用户反馈 | 用户看到或听到的结果。话术未定时标为「示例」 | 确认实际起播后，播报「已播放下一个」。 |
| 验收 | 用什么可观察的结果判断通过 | 核对内容已切到正确的一集，播放器实际开始播放。 |

六项是信息要求，可在短段、步骤或表格里合并呈现。同义说法执行一致时合并。按需补充会改变结果的判断顺序、权限、异常和替代路径。例如，同一句「下一集」在以下三个场景中有不同结果。

| 场景 | 系统动作 | 用户反馈（示例） | 验收 |
| --- | --- | --- | --- |
| 当前示例视频应用有下一集 | 切到下一集并播放 | 已播放下一个 | 切到正确的一集且实际起播 |
| 当前示例视频应用已是末集 | 保持当前内容和播放状态 | 后面没有视频可以播放 | 内容未切换，原播放或暂停状态保持 |
| 示例视频应用有下一集，播放器明确返回切换失败 | 保持当前内容，反馈切换未完成 | 暂时无法切换 | 当前集未变化，且未播报成功 |

下线时也写同样的六项，补齐相近的保留动作、提示或替代路径，以及反向验收。例如，「用示例视频应用播放某片」触发停用规则，提示暂不支持在示例视频应用内语音点播，验收时检查应用未被自动拉起、也未切换信源。「打开示例视频应用」仍走应用开启规则，单独验收。

## 三、什么时候用流程图和高亮块

| 内容 | 用什么 | 怎么放 |
| --- | --- | --- |
| 步骤顺序、条件分支、跨角色或跨系统流转难以一眼看清 | 飞书文档里的流程图 | 放在对应策略小节，先让读者看清从哪开始、在哪里判断、各分支怎样结束。标清动作主体、关键条件、成功结果和适用的失败或回退路径。图中的术语与正文一致。 |
| 简单的线性操作、能力对比或反馈与验收的精确对照 | 短步骤或表格 | 用步骤表达顺序，用表格对齐条件与结果。复杂策略可先放流程图讲路径，再用表格补齐每个分支的规则。 |
| 子章节里会影响决策、实现或验收的结论、限制或待确认项 | 飞书高亮块 | 就地放在相关内容旁。每个块聚焦一个重点，例如数据只能回答什么、某条件下必须拦截、评审还要决定什么。 |

写入流程图时优先用飞书原生画板。按需查阅飞书 CLI 的 `lark-doc/references/lark-doc-whiteboard.md`。回读并预览实际画板，确认有内容，再核对起点、分支和结果。

例如，示例视频应用的语音控制可用一张流程图展示「收到指令 → 判断是开关、基础播控还是已下线能力 → 确定对象 → 执行或反馈」。章节内可高亮「已到末集时保持当前内容和播放状态」，再用验收表写明具体检查。

## 四、资料和数据怎么用

| 手里有什么 | 用来做什么 |
| --- | --- |
| 参考 PRD（可选） | 用户提供时可核对团队术语、排版和现行规则。旧规则需要确认适用于本次需求。写作与验收按本标准执行。 |
| 资料助手的完整报告 | 从能力对照、场景、话术、异常和缺陷中逐项找可复用细节。把会影响结果的内容落实到本版范围、策略或验收中。 |
| 原始 PRD、纪要、消息和缺陷 | 核对关键判断的时间、对象和状态。分别说明旧版设计、历史问题、当前能力和本版决定。证据有冲突时，把待核范围限定在受影响的规则。 |
| 历史及本轮数据 | 核对各自的窗口、对象、事件和去重。不同口径分开写。应用使用、实际起播、语音请求和执行成功分别表述。「未见客诉」写明记录时点。 |

修订时先读现稿，保留仍有效的结论、数据和引用。已有数据能回答问题时直接复用。需要新增取数时，按 [技能主文件](../SKILL.md) 选择并确认取数路径。正文按「已定规则」「本次建议」「待确认」标清状态，出处集中放在需要追溯的位置。

## 五、交付前怎么检查

- **第一次接触业务的读者能复述。** 只读摘要和背景，就知道服务谁、解决什么、这次改哪里。继续读一个策略，能说出触发条件、执行对象和结果。遇到必须靠口头补充的内容，补进正文。
- **评审者能说清为什么改。** 背景保留了关键决策理由，数据的口径与边界写清。
- **研发能按场景实现。** 同一句话在不同状态下命中哪个对象、做什么、怎么反馈，都找得到。
- **测试能判定通过。** 主流程、边界、历史缺陷和下线反向用例有可观察结果。
- **扫读能找到重点和路径。** 高亮出现在读者需要判断的位置。流程图的动作、条件和结果与策略表一致。
- **写回飞书后回读。** 至少核对一条保留规则、一条下线或异常规则和一个关键数据口径。使用了流程图或章节高亮时，确认对应飞书块实际存在。
